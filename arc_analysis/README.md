# ARC 분석 — 축소 실험의 전이 가능성과 공간 등변 편향

`lt/train_arc.py` 를 그대로 전 규모로 돌리기 전에 답해야 할 두 질문을 조사했다.

1. 과제를 축소한 조건에서 얻은 우위(ablation)가 최종 학습에서도 유지된다고 믿을 수 있는가.
2. 데이터 증강(D4 8종 × 색 치환 × 평행이동, 과제당 1,000개)을 덜 쓰도록 모델에 등변 편향을 넣을 수 있는가.

이 폴더의 코드는 `lt/` 를 import 만 하고 수정하지 않는다.

## 1. 비용의 실체

URM 의 ARC 기본 설정은 `epochs=200000`, global batch 768, GPU 8장이다. 1 epoch 은 960 과제 그룹에서 증강 퍼즐 하나씩을
뽑아 그 예제(평균 4.15개)를 쓰므로 epoch 당 3,988 예제, 전체 **7.98×10⁸ 예제 ≈ 1.04×10⁶ step@768** 이다.

4090 한 장에서 v1.1 폭(832·8헤드·8블록) LT 의 1 세그먼트 fwd+bwd 를 재었다 (`bench_canvas.py`, bf16 autocast).

| 캔버스 S | T=S² | 배치 | s/step | **ms/예제** | 최고 메모리 |
|---|---|---|---|---|---|
| 30 | 900 | 2 | 0.063 | 31.4 | 3.9 GiB |
| 30 | 900 | 8 | 0.249 | 31.1 | 14.8 GiB |
| 30 | 900 | 11 | 0.340 | 30.9 | 20.2 GiB |
| 20 | 400 | 32 | 0.264 | 8.2 | 14.5 GiB |
| 15 | 225 | 64 | 0.232 | **3.6** | 11.7 GiB |
| 10 | 100 | 128 | 0.154 | **1.2** | 7.7 GiB |

- `train_arc.py` 기본 배치 2는 지연시간에 묶여 S 와 무관하게 0.063 s/step 이다. 배치를 키워야 GPU 가 찬다. S=30 은 배치 11 까지.
- 예제당 비용은 S=30 → 15 에서 8.6배, → 10 에서 26배 준다. 결합 기억 `w[B,H,T,T]` 와 어텐션이 T² 이라 (S/30)⁴ 로 줄기 때문.
- URM 예산의 **1%** 만 돌려도 S=30 은 69시간, S=15 는 8시간, S=10 은 2.7시간이다. 10% 는 각각 29일 / 3.3일 / 1.1일.
- 퍼즐 ID 임베딩 테이블은 960 과제 × 1,000 증강 × 832 fp32 ≈ 3 GiB 로, 배치와 무관하게 고정이다. 증강 수를 줄여야만 준다.

캔버스 축소로 살아남는 과제 (`grid_size_stats.py`, 과제의 모든 입출력 격자 최대 변 기준):

| subset | 과제 | ≤10 | ≤12 | ≤15 | ≤20 |
|---|---|---|---|---|---|
| training | 400 | 178 (44%) | 220 (55%) | 266 (66%) | 342 (86%) |
| evaluation | 400 | 77 (19%) | 114 (28%) | 189 (47%) | 282 (70%) |
| concept | 160 | 39 (24%) | 65 (41%) | 108 (68%) | 144 (90%) |
| 전체 | 960 | 294 (31%) | 399 (42%) | 563 (59%) | 768 (80%) |

## 2. 축소 실험의 우위가 최종 학습으로 전이되는가

### 2.1 결론부터

**증명은 불가능하다.** 규모에 따라 아키텍처 순위가 뒤집히는 사례는 문서화되어 있다 (Tay et al. 2022, *Scaling Laws vs Model
Architectures*, arXiv:2207.10551 — 소규모에서 이기던 귀납 편향이 대규모에서 지는 경우와 그 반대를 모두 보고). 할 수 있는 것은
(a) 전이가 잘 되는 종류의 주장만 축소 조건에서 검증하고, (b) 2~3 단의 사다리에서 격차의 **부호와 추세**를 확인해 전이 가능성의
증거를 쌓는 것이다.

### 2.2 어떤 축을 줄이느냐가 전이 신뢰도를 결정한다

| 축 | 절감 | 무엇이 바뀌는가 | 전이 위험 |
|---|---|---|---|
| **캔버스 30→15 (과제 필터)** | 예제당 8.6×, w 16×, 배치 64 가능 | 토큰 수만. 폭·헤드·블록·세그먼트·η·λ·α 의 동역학은 그대로 | 낮음. 단 부분집합이 작은 격자 쪽으로 치우쳐 절대 점수는 전이 안 됨. 장거리 상호작용(α 작은 헤드)이 필요한 기제는 검증 못 함 |
| **증강 수 1000→125** | ID 테이블 8×, 데이터 다양성 | 네트워크가 보는 방향·색 조합의 수. 투표 앙상블의 크기 | 중간. 이것 자체가 §3 의 측정 대상 |
| 과제 수 | 선형 | 공유 가중치가 배우는 규칙의 수. ID 암기가 상대적으로 쉬워짐 | **높음**. "규칙 간 일반화" 체제가 달라진다. 캔버스 필터로 이미 줄어드니 추가로 줄이지 말 것 |
| 폭 832→256, 블록 8→4 | 선형~제곱 | 모델 체제 자체. LT 의 √d 게이지·γ=1/d 는 폭에 걸려 있고, μP 식 전이는 폭에만 성립 (Yang et al. 2022) | **높음**. 하지 말 것 |
| 배치 2→64 | — | 원본 768 에 가까워짐 | 오히려 원본에 **더 충실**해진다. 축소의 부산물이 아니라 이득 |

즉 **폭·깊이·과제 수는 고정하고 토큰 수와 증강 수만 줄이는 것**이 원칙이다. 캔버스 축소는 지금 코드에서 안 된다 —
URM builder 의 `ARCMaxGridSize=30` 고정, `ARCSplit` 의 `seq_len==900` 검사, `crop_grid` 의 `reshape(30,30)`, 이 셋을 S 로
매개변수화하고 builder 에 과제 필터를 넣어야 한다 (작은 패치).

### 2.3 전이되는 주장과 안 되는 주장

- **기제가 정확한 주장은 부호가 전이된다.** "등변 모델은 D4 증강이 필요 없다"는 통계적 관측이 아니라 항등식이다 (§3.3 에서
  fp32 오차 수준으로 확인). 축소 조건에서 잴 것은 부호가 아니라 *크기* — 증강을 1/8 로 줄였을 때 손실이 실제로 0 에 가까운지,
  같은 파라미터 예산에서 성능이 얼마나 오르는지다.
- **용량·최적화에 관한 주장은 취약하다.** "블록 순서 post 가 낫다", "흔적 z 가 낫다" 같은 것은 T=225 에서의 결과가 T=900 을
  말해 주지 않는다. Sudoku 에서 v1.7 의 변동계수 20% (README) 가 보여주듯 LT 는 런 간 분산이 크므로 이런 비교는 seed 3개 이상 없이는
  축소 조건에서도 결론이 안 난다.
- **ARC 평가는 전도적(transductive) 이다.** evaluation 과제의 시범 예제를 학습하고 질의만 평가하며, 질의는 같은 퍼즐 ID 를 쓴다.
  ARC Prize 팀의 HRM 분석(2025)은 이 설정에서 성능의 대부분이 아키텍처가 아니라 증강 + 외부 정련 루프 + ID 임베딩에서 온다고
  보고했다 (수치는 원문 확인 필요). 따라서 증강 수를 바꾸는 실험은 "일반화"가 아니라 "과제당 몇 개의 시점을 보여 주면 ID 가 규칙을
  담는가"를 재는 것이고, 이 축은 캔버스 크기와 거의 독립이라 전이가 잘 될 것으로 본다.

### 2.4 제안하는 사다리

```
S=10  (294 과제, 배치 128)   증강 {1000, 250, 60}  × {기존 LT, D4LT}  × seed 3     ← 1 조건 ≈ URM 예산 0.3% 에 1시간
S=15  (563 과제, 배치 64)    같은 격자에서 격차의 부호·크기가 유지되는가                 ← 1 조건 ≈ 8시간
S=30  (960 과제, 배치 11)    사다리에서 살아남은 1~2 조건만                              ← 조건당 수일
```
판단 규칙은 실험 전에 적어 둔다: "S=10 과 S=15 에서 부호가 같고 S=15 의 격차가 S=10 보다 작지 않으면 S=30 으로 올린다."
끝점 대신 학습 곡선을 비교한다 — 곡선이 교차하면 사다리 위에서 뒤집힐 신호다.
지표는 pass@K 만이 아니라 LT 의 존재 이유인 **외삽 기울기** (`--eval-segments` 16 → 64 → 128 에서 pass@K 변화) 를 같은 부분집합에서 잰다.

## 3. 공간 등변 편향

### 3.1 LT 가 지금 가진 대칭성 (`equivariance_check.py`, 무작위 초기화, 12×12 캔버스, d=128, 2세그×3블록)

**평행이동.** 읽기·쓰기 커널은 `θ_j·(pos_t − pos_n)` 과 `‖Δ‖₁` 만 쓰므로 위치는 상대적이고, 무한 캔버스에서는 정확히 등변이다.
유한 캔버스에서는 PAD 칸과 캔버스 가장자리가 깨뜨린다:

| 격자 5×4 오프셋 | (0,1) | (1,0) | (2,3) | (7,8) | (2,3), α≈2.1 로 고정 |
|---|---|---|---|---|---|
| 격자 칸 로짓 상대 오차 | 0.59 | 0.53 | 1.20 | 1.61 | **0.022** |

오차는 거리 감쇠 α 가 작을수록 크다. Sudoku v1.1 체크포인트의 학습된 α 는 헤드별 0.02~0.31 로 도달 거리 1/α 가 캔버스를
덮는다. 따라서 **평행이동 증강은 LT 에서도 완전히 불필요하지는 않다** (가장자리 강건성을 가르친다). 다만 절대 위치를 배울 필요는
없으므로 URM 이 절대 위치 임베딩 때문에 넣은 것만큼 필수는 아니다. 증강 안에서 ID 를 공유하니 비용도 없다. 그대로 두고 끄는 실험만
한다.

**D4.** 캔버스 전체를 회전·반사하면 로짓 상대 오차 0.74~1.53 — 등변이 아니다. 원인은 `θ_j ∈ R²` 가 방향을 가진 주파수 벡터라는 점
하나다 (RoPE-Mixed, Heo et al. 2024 와 같은 형태). `‖Δ‖₁` 감쇠, 값 수송, 경계 MLP, 주입, Φ 는 모두 이미 등변이다.

**색.** `nn.Embedding(12, d)` — 대칭성 없음.

**부호화 자체도 D4 대칭이 아니다.** URM builder 는 EOS 를 출력 격자의 오른쪽·아래에만 놓고 격자를 좌상단에 고정한다. 회전한 과제도
EOS 는 다시 오른쪽·아래다. 그러므로 네트워크를 정확히 등변으로 만들면 EOS 위치가 틀린다. 등변 모델을 쓰려면 EOS 를 빼고 **출력 둘레
한 칸의 PAD 를 감독**하는 대칭 부호화로 바꿔야 한다 (`crop_grid` 는 PAD 도 경계로 취급하므로 평가 코드는 그대로 된다).

### 3.2 "불변 커널" 로는 안 되는 이유

가장 싼 방법 — `θ_j` 를 D4 궤도 `{M_g θ_j}` 로 묶고 W_C·ψ·β 를 궤도 안에서 공유 — 는 커널을 D4 불변으로 만든다. 그러나
D4 에 −I 가 있으므로 `Σ_g cos(Δφ + (M_gθ)·Δ + ψ) = cos(Δφ+ψ)·K(Δ)` 로 **위상과 위치가 분리**된다. "위상이 방향을 부호화한다"는
LT 의 주소 기제가 사라진다.

더 근본적으로, 은닉 상태가 방향 정보를 안 가지는 등변 모델은 **방향이 있는 규칙을 표현할 수 없다.** f 가 등변이면 f(회전 x) = 회전 f(x)
인데, "오른쪽으로 옮겨라"는 대칭인 입력(점 하나)에 대해 f(점) = 오른쪽 점 = 아래 점 이어야 하므로 모순이다. ARC 과제는 대부분
방향이 있다. URM 은 이 대칭을 **증강 사본마다 다른 퍼즐 ID** 로 깨뜨린다. 등변 모델에서는 대칭을 깨는 역할이 퍼즐 임베딩에 있어야 하고,
그러려면 임베딩과 은닉 상태가 D4 의 **비자명 표현**(정칙표현)에 살아야 한다: f(g·x ; g·e) = g·f(x ; e). 그러면 회전한 과제 =
같은 임베딩을 회전한 것이고, 8 방향 증강 사본이 ID 하나를 공유한다.

### 3.3 D4LT 시제품 — 헤드 축 = D4 정칙표현 (`lt_d4.py`, 구현·검증)

LT 의 헤드 수 8 = |D4| 라는 점을 쓴다. `LT_Inner.step / _forward` 는 한 줄도 안 바꾸고 파라미터만 묶었다.

| 구성 요소 | 원본 | D4LT |
|---|---|---|
| 은닉 상태 h ∈ R^{8·dh} | 헤드별 슬라이스 (w_sh 블록대각 init) | 슬라이스 k = 군 원소. (g·h)_x[k] = h_{g⁻¹x}[g⁻¹k] |
| 주소 W_C, 값 w_sh | 헤드마다 [dh, d] 독립 | 슬라이스 축 G-합성곱 (블록(k,k') = base[k⁻¹k']). 헤드 m = 출력 슬라이스 m. QR 은 헤드 0 에 한 번, 나머지는 열 순열 |
| 위치 주파수 θ | 헤드마다 [p,2] 독립 | θ^{(m)} = M_m θ (하나의 θ 를 8 방향으로 회전) |
| ψ, β, α, η, λ, g | 헤드별 | 공유 |
| 경계 MLP | Linear(d, 2·2304), Linear(2304, d) | 두 층 모두 슬라이스 축 G-합성곱, 게이트 곱은 슬라이스 안. 중간폭 8×288 = 2304 동일 |
| 입력 임베딩 | [12, d] | [12, dh] 를 8 슬라이스에 타일 (자명표현) |
| 퍼즐 임베딩 | 증강 사본마다 행 | (과제, 색치환) 당 행 [8, dh]; 방향 g 는 슬라이스 순열 |
| 판독 w_cls | Linear(d, 12) | 슬라이스 합 → Linear(dh, 12) (불변) |
| 파라미터 (임베딩 제외) | 232,748 (d=128) | 29,104 — **1/8** |
| 상태·w 크기, 어텐션 FLOPs | | 동일 |

검증 (fp32, 캔버스 전체 변환 + 임베딩 방향 함께 변환, 세그먼트 2개 = 결합 기억 w 이월 포함):

| g | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| 로짓 상대 오차 | 1.2e-6 | 1.1e-6 | 1.3e-6 | 1.3e-6 | 8.3e-7 | 1.3e-6 | 1.3e-6 |
| w[m,t,n] 상대 오차 (헤드 m→g·m, 위치 (g·t, g·n)) | 4.7e-7 | 4.8e-7 | 5.0e-7 | 5.2e-7 | 2.7e-7 | 4.4e-7 | 5.0e-7 |

대조: 입력만 회전하고 임베딩 방향을 고정하면 오차 1.14 — 규칙의 방향이 임베딩에 있다는 뜻이고, 이것이 의도한 동작이다.

**얻는 것.** 네트워크에게 D4 증강은 캔버스 가장자리 효과를 빼면 항등 연산이 된다 → 과제당 증강 1,000 = 125 색치환 × 8 방향에서
방향 축이 사라지므로 ID 테이블 1/8 (≈0.37 GiB), 같은 색치환 수에서 데이터 8배 절약. 학습된 원시 연산(선 긋기, 채우기 …)이 8 방향에서
자동으로 공유된다.

**잃는 것·해야 할 것.**
- 자유 파라미터 1/8. 상태 크기는 그대로다. 보정하려면 H=16 (2 종류 × 8 방향, w 메모리 2배) 또는 dh 확대.
- 8 방향 투표가 동일 예측으로 붕괴한다 → 앙상블 다양성은 색치환 축만 남는다. ARC Prize 의 HRM 분석대로 투표가 성능의 큰 몫이면 손실이 있을 수 있다. 측정 대상.
- 대칭 부호화 (EOS → PAD 둘레 감독) 로의 전환. URM 인터페이스와 어긋나므로 `train_arc.py` 의 라벨 처리와 builder 후처리가 필요.
- 퍼즐 ID 재사상: `name|||tK|||perm` → (name, perm) 행 + 방향 K. 현재 builder 는 (K, perm) 을 무작위로 뽑으므로 같은 perm 의 8 방향이
  생기지 않는다 — 증강 생성을 "perm 125개 × 방향 8" 로 바꾸거나, 등변이므로 그냥 perm 125개만 만들면 된다 (방향은 무의미).
- sparse SignSGD 경로에서 슬라이스 순열의 역을 gradient 에 적용한 뒤 scatter 해야 한다 (시제품은 밀집 파라미터).
- 헤드를 묶었을 때 LT 의 위상 동역학(η, λ 공유)이 Sudoku 만큼 안정한지는 미지수. Sudoku 는 D4 대칭이 아니므로 거기서 검증할 수는 없고 S=10 사다리에서 직접 본다.

### 3.4 색 — 정규화만으로는 부족하다 (`color_canon_stats.py`)

시범 예제(입력+출력)의 색 빈도 순위로 색을 재명명하는 정규화(canonicalization; Kaba et al. 2023 의 고정 버전)를 검토했다.
검정은 URM 처럼 고정.

| subset | 빈도 동률 있음 | 동률이 상위 3색 안 | **질의 입력에 시범에 없던 색** | 시범 색 수 |
|---|---|---|---|---|
| training | 36% | 20% | **35%** | 4.6 |
| evaluation | 31% | 13% | **29%** | 5.0 |
| concept | 36% | 15% | **77%** | 4.6 |

질의에 새 색이 나오는 과제가 1/3 (concept 은 3/4) 이라는 것은 ARC 의 색 대칭이 두 종류라는 뜻이다 — 과제 전체에서 색이 고정된
과제("빨강을 지워라")와 예제마다 색이 다른 과제("표식 색으로 칠해라"). 과제 단위 정규화는 전자만, 예제 단위 정규화는 후자만
맞는다. 증강은 둘 다 처리한다. 따라서 정규화는 색치환 증강을 대체하지 못하고 줄이는 보조 수단이다.

색을 진짜 등변으로 다루려면 칸 상태에 색 축을 두어야 한다 (h_t ∈ R^{10×d'}, 색 슬롯 간 가중치 공유, DeepSets 식 합 풀링;
CompressARC, Liao & Gu 2025 가 이 방향). LT 에 넣으면 주소 û_t 는 색 불변 풀링에서, 값 v_t 는 색 슬롯별로, `agree = ⟨v̂_t, v̂_n⟩`
는 슬롯 겹침으로 "같은 색" 을 자연스럽게 잰다. w 는 색과 무관한 공간 결합이라 크기가 안 변한다. 그러나 주소가 색을 못 보게 되는 것이
LT 의 위상 주소 기제와 맞는지 알 수 없고, 변경 규모가 D4 보다 훨씬 크다. D4LT 결과를 본 뒤의 두 번째 단계로 둔다.

### 3.5 정리 — 증강 세 축과 대응

| 증강 | LT 현재 | 편향으로 대체 | 비용 | 판단 |
|---|---|---|---|---|
| 평행이동 | 근사 등변 (가장자리 효과) | 없어도 큰 손실 없을 것으로 예상 | 0 (ID 공유) | 그대로 두고 끄는 실험만 |
| D4 (8종) | 비등변 | **D4LT 로 정확히 대체** | 파라미터 1/8, 부호화 변경, 투표 다양성 감소 | 1 순위 실험 |
| 색 치환 (9!) | 비등변 | 정규화는 부분적, 등변화는 큰 변경 | — | 증강 유지하되 수를 줄이는 곡선 측정 |

## 4. 진행 상황

### 1단계 — 캔버스 매개변수화 (완료, 2026-09-13)

`prep_arc_canvas.py` 는 과제를 최대 변 ≤ S 로 거른 뒤 URM builder 의 모듈 상수 `ARCMaxGridSize` 만 S 로 바꿔 실행한다
(builder 파일·부호화·증강·ID 규칙은 원본 그대로, `provenance.json` 에 패치와 필터를 기록). `train_arc_s.py` 는 `train_arc.py` 의
900/30 상수 세 곳(`ARCSplit` 검사, `crop_grid`, `main` 의 모델 cfg)만 데이터의 `seq_len` 에서 읽은 S 로 바꿔 끼우고 나머지 코드를
그대로 실행한다. `lt/` 는 수정하지 않았다.

검증: 합성 S=10 데이터에서 크롭·역증강·샘플러·투표·중간 저장/재개 비트 일치(기존 lt 검사와 같은 내용), 공식 builder 출력에서
학습→평가→제출 JSON, S=30 에서 `crop_grid` 가 원본과 동일. 5개 모두 통과. `lt.test_train_arc` 4개도 그대로 통과.

실데이터: `data/arc_s10_aug250` (294 과제, 증강 250, ID 71,593, 68 MB, builder 39 초. 색이 적은 과제는 중복 제거로 증강이 72 개까지만
생긴다). 4090 스모크 `runs/arc_s10/smoke`: v1.1 폭·배치 128·300 step 에 88 초 = **2.3 ms/예제** (샘플러 포함), loss 2.45 → 0.54.
`train_arc.py` 가 찍는 `tokens=900`, `coupling carry alone=3164 MiB` 줄은 원본 main 의 상수라 무시한다 — 실제 값은 바로 위 `[ARC-S]` 줄.

S=10 사다리 한 조건(20k step × 128 = 2.56M 예제 ≈ URM 예산 0.3%)은 약 100 분이다.

### 2단계 — D4LT 통합과 S=10 증강 곡선 (실행 중, 2026-09-13 시작)

**D4LT 통합.** `lt_d4.py` 의 `D4Inner` 가 원본 `CastedSparseEmbedding`(sparse SignSGD)·EMA·AdamATan2 경로에 그대로 붙는다.
정칙표현 퍼즐 임베딩은 평평한 d 벡터를 [8, dh] 로 읽는 것이라 원본 임베딩을 그대로 쓴다. **ID 재사상과 방향 순열은 불필요**한 것으로
판명됐다: URM 처럼 증강마다 행을 두면 한 행이 한 방향에서만 학습되므로 슬라이스 순열은 행의 재명명일 뿐이고, 등변이므로
`num_aug` 를 1/8 로 줄이는 것이 곧 "방향 축 제거"다. 통합 후 등변성 재검증: 로짓 오차 ~1e-6, w 오차 ~7e-7.

**대칭 부호화** `--encoding frame`: EOS 토큰을 입력·출력 격자의 4변 테두리(모서리 포함)에 놓는다. 테두리는 감독, 나머지 PAD 는
무시 — URM 의 "오른쪽·아래 EOS 감독" 을 D4 대칭으로 확장한 것. `crop_grid` 는 그대로 동작한다. 곡선 실험은 base 도 frame 으로
돌려 부호화를 통제한다 (base 의 urm 부호화 결과와 직접 비교하지 말 것).

`train_arc_s.py --model base|d4 --encoding urm|frame`. 재개 시 out-dir 의 `arc_s.json` 에서 읽고 CLI 와 다르면 거부.
검사 7개 통과 (frame 부호화, d4 학습→저장→재개 비트 일치, builder 데이터에서 base·d4 끝까지).
d4 GPU 스모크 `runs/arc_s10/smoke_d4`: 폭 832·배치 128·300 step 50 초, loss 3.66 → 0.39.

**사다리 설계** (`run_ladder_s10.py`, seed 0 하나):

| | 증강/과제 | 비고 |
|---|---|---|
| base | 1000, 250, 60, 8 | |
| d4 | 1000, 125, 31, 8 | 125·31 = base 의 1000·250 의 1/8. 양 끝 1000·8 은 두 곡선 공유점 |

20k step × 배치 128, warmup 2k, 중간 평가 2k step 마다(증강 32 상한, seg16), 끝에 전체 증강 seg16 + seg128 외삽(증강 128 상한).
판정: base(N) 와 d4(N/8) 의 pass@K 가 같거나 d4 가 위면 "D4 증강은 잉여" 성립. 결과는 `runs/arc_s10/ladder_summary.json`,
`python arc_analysis/summarize_ladder_s10.py --out runs/arc_s10/ladder`.

```bash
python arc_analysis/prep_arc_canvas.py --urm-repo /tmp/URM --canvas 10 --num-aug 1000 --output-dir data/arc_s10_aug1000
python arc_analysis/train_arc_s.py --data data/arc_s10_aug250 --out-dir runs/arc_s10/base_aug250_s0 --seed 0 \
    --batch-size 128 --max-steps 20000 --eval-every 2000 --eval-segments 16
python arc_analysis/train_arc_s.py --data data/arc_s10_aug250 --out-dir runs/arc_s10/base_aug250_s0 \
    --resume runs/arc_s10/base_aug250_s0/latest.pt --eval-only --eval-segments 128      # 외삽
```

### 2단계 중간 관찰 (2026-09-13, S=10 · 증강 8 · d4 · seed 0)

- 4k step 에 첫 완전 일치, 14k 에 pass@1 0.013 / pass@10 0.052 / 완전 일치 9~11 (과제 5종). 학습 loss 0.005 (시범은 외움).
- **세그먼트 외삽 없음**: 9k·11k 체크포인트를 16/32/64/128 세그로 돌려도 pass@K 동일, 완전 일치 ±1.
  8 세그먼트 단위 진화 그림(`runs/arc_s10/figs/d4_aug8_11k_evolution128.png`)에서 **seg 8 이후 128 까지 바뀌는 픽셀이 0**.
  진단: URM 프로토콜은 규칙을 ID 임베딩에 두어 forward 안에 검사 대상이 없고, 매 세그먼트 정답 감독은 첫 세그먼트에 답을
  내고 유지하는 것을 최적으로 만든다. Sudoku 외삽의 두 조건(한 세그먼트로 못 풂 + 모순을 자기 검사)이 둘 다 없다.
- 남은 의미 있는 ablation 은 w 제거 하나: `d4_aug8_nostdp` (`--no-stdp`) 를 같은 조건으로 돌리는 중.
- 증강 곡선 사다리(base×4, d4×4)는 사용자 결정으로 중단 (base_aug8 7k, base/d4_aug1000 6.7k 체크포인트는 재개 가능).

### 3단계 — in-context 프로토콜 (구현 완료, 미실행)

설계는 `protocol_context.md`. 요지: 시범 쌍 K 개 + 질의를 슬롯으로 한 시퀀스(T = 2(K+1)·S²)에 두고, 위치는 슬롯 안 칸 좌표로,
커널 위상에 슬롯별 σ 를 더하고(분리형이라 비용 0, D4 판은 헤드 공유로 등변 유지), 역할 임베딩을 주입, 퍼즐 ID 임베딩 제거.
학습은 leave-one-out(질의 무작위) + 선택적 시범 출력 마스킹, 손실은 질의 출력 슬롯만. inductive(evaluation 과제 미학습)가 기본.
검사 3개 통과, GPU 스모크(d4·폭 832·K=2·600 토큰·배치 8) 정상. 실행 예:

```bash
python arc_analysis/train_arc_ctx.py --data data/arc_s10_aug8 --out-dir runs/arc_s10_ctx/d4_k2 --model d4 --k-demos 2 \
    --mask-prob 0.3 --batch-size 16 --max-steps 20000 --eval-every 2000 --eval-max-augmentations 8
```
판정 기준은 protocol_context.md §6 (seg 8 이후 픽셀 변화 → seg16→64 완전 일치 증가 → inductive pass@2 > 0).

### 3단계 결과 — in-context 런 (d4_k2, 20k, 2026-09-13)

배치 16 · K=2 · ID 유지 · 마스킹 없음. 20k 에 토큰 정확도 0.649, 완전 일치 2, pass@10 0.026. 사후 점검(대화 기록):
(1) 배치 16 vs 128 이라 같은 step 에서 예제 수가 8배 적었고, 예제 수 기준으로는 URM 판과 동등; (2) ID 가 있고 마스킹이
없어 시범이 사용되지 않음 (ID 임베딩 노름이 URM 판과 동일 3.18 vs 3.14, 학습 loss 0.008); (3) 슬롯 위상 σ 를 0 으로 초기화해
20k 뒤에도 std 0.03 — 기제가 꺼져 있었음. 따라서 이 런은 가설을 시험하지 못했고, 재시험하려면 ID 드롭아웃 + σ 무작위 초기화 +
예제 수 맞춤이 필요하다. 현재 보류.

### STDP ablation 결과 (d4_aug8 vs d4_aug8_nostdp, 20k)

8~10k 에서 w 있는 쪽이 완전 일치 2배(8 vs 5, 11 vs 6), 12~16k 에 동률, 20k 에 17(9과제) vs 7(3과제). 9 지점 중 8 곳에서 stdp 우위,
크기는 seed 1개로 확정 불가. 읽기: w 는 초반 수렴을 빠르게 하고 끝점에서도 우위 경향. 세그먼트 외삽은 둘 다 없음.

### 4단계 — v3 (색 슬롯 등변 풀버전) vs d4 (완료, 2026-09-13)

`lt_v3.py` = 사용자가 준 풀버전 train.py 의 모델 코드 그대로 (2.83M 파라미터, 결합 경로 83%, 색 순열 등변 오차 7e-7 확인).
`runs/arc_s10/v3_aug8`: 증강 8 · seed 0 · frame · 20k · 배치 128 — d4_aug8 과 동일 조건. 0.52 s/step.

| 8k | 0.013 / 0 | 0.013 / 0 | 0.045 / 0.045 | 0.720 / 0.706 | 8(4) / 3(3) |

### 5단계 — sheaf 확장 (실행 중)

W_sh 를 제한사상으로 읽으면 LT 수송은 sheaf 확산의 절반(차수 항 없음). `lt_v3.py` 에 두 플래그를 더했다 (기본값은 원본과 수치 동일, 검사로 확인):
- `--transport laplacian`: `h += Σ_n a_tn FᵀF (h_n − h_t)` — Dirichlet 에너지 `E = ½ Σ a⁺_tn ‖F h_t − F h_n‖²` 의 경사 하강 형태
- `--sheaf-cond scale`: 퍼즐별 제한사상 `F_h(e) = diag(1+s_h(e)) W_sh,h`, s 는 ID 임베딩 뒤 H·c=128 차원 (0 에서 시작, ID 폭 140→268)
- 세그먼트별 E 를 outputs 에 노출, `probe_energy.py` 로 E(seg) vs 정답 여부.
동기: ARC(URM 프로토콜)엔 forward 안에 검사 대상이 없어 반복이 정지한다는 진단 → E 가 자기 일관성 척도가 되면 세그먼트 반복 = 제약 만족.
v3 원본 14k 체크포인트에서 이미 맞은 사본의 E(1.5M)가 틀린 사본(2.5M)보다 낮았음 (원본 질의 88개, 표본 작음).
`runs/arc_s10/v3sheaf_aug8`: v3 와 동일 조건 + laplacian + scale. in-context no-ID 재실험(구현 완료)은 사용자 결정으로 보류.
